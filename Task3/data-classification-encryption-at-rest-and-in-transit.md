# Task 3 — Классификация данных, обоснование защиты, инструменты (at rest / in transit)

Кейс «Медикаменте». As-Is и процессы согласованы с [Task 1](../Task1/data-privacy-problems-and-dfd-index.md); целевой контур и аналитика — с [Task 2](../Task2/c4-context-and-mvp.md) и [Task 6](../Task6/c2-classification-engine.md).

**Дисклеймер:** квалификация категорий по 152-ФЗ и режиму медицинской тайны — **инженерные допущения** для проектирования; финальная трактовка — зона DPO/юриста.

---

## 1. Модель уровней чувствительности (для трассировки к мерам)

| Уровень | Код | Смысл | Примеры из кейса |
|---------|-----|--------|------------------|
| Низкий | **L1** | Данные без персонального контекста или обезличенные агрегаты | Обезличенная статистика нагрузки (To-Be) |
| Средний | **L2** | Обычные ПДн, утечка которых создаёт репутационные и комплаенс-риски | ФИО, телефон, e-mail в журналах и CRM |
| Высокий | **L3** | ПДн повышенной чувствительности, финансы, расширенный профиль | Адрес, место работы, суммы оплат, договоры |
| Критичный | **L4** | Медицинские данные, специальные категории по смыслу кейса | Жалобы, диагнозы, заключения, лабораторные показатели, сканы медкарт |

Классы данных ниже сопоставлены с **L2–L4**; для каждого указаны типовые состояния **at rest** (файлы, БД, бэкапы) и **in transit** (SMB, OLE, SMTP, HTTPS в To-Be).

| **CLS-04** | **Платёжные / финансовые:** суммы, договоры, кассовые операции | L3 | Регуляторные и мошеннические риски; связь с персоной | **1С** файловый режим, Excel-касса (теневой дубль) | ККМ ↔ 1С по **TCP/OLE** без прикладного шифрования | **As-Is:** физическая безопасность ККМ, учётные записи 1С. **To-Be:** единый платёжный контур, отказ от теневого Excel, **HSM/токены** при интеграции — по проекту; журналирование операций в СУБД |
| **CLS-05** | **Сведения о здоровье:** жалобы, анамнез, заключения врача | L4 | Ядро медицинской тайны в смысле кейса; максимальный ущерб при утечке | JPG/PDF на файловом сервере, Excel | Неформализованные каналы **P7**, почта | **To-Be:** раздельные контуры хранения, шифрование вложений, **RBAC/ABAC**, аудит; доступ врача по назначению |
| **CLS-06** | **Лабораторные результаты:** показатели, реестры | L4 | Реидентификация состояния здоровья и связь с субъектом | `RegistryByDate.xlsx`, папка Laboratory Registry | Будущий **API лаборатории** — граница доверия | **To-Be:** минимизация полей API (см. | **CLS-07** | **Медицинская карта (совокупность):** сканы, выписки | L4 | Полный профиль пациента; цель бизнеса — «усилить безопасность медкарт» | Общий диск без шифрования at rest | Копии на ПК, USB (вне контролируемого учёта) | **To-Be:** ЕМК/архив с шифрованием, WORM/retention по политике, **теги** на данных (roadmap To-Be), CI-проверки |
| **CLS-08** | **Кадровые и ЗП** (в контуре 1С бухгалтерии) | L3 | Спецкатегории в законе могут пересекаться; в кейсе — чувствительный учёт | Файл 1С на сервере | OLE между приложениями | **As-Is:** ограничение доступа к каталогу 1С. **To-Be:** сегментация, бэкапы шифрованные, MFA для администраторов |
| **CLS-09** | **Аналитика / BI:** выгрузки, ноутбуки Jupyter | L2–L4 (смешение) | Смешение ПДн и операционки без классификации (**PRV-010**) | Ноутбуки локально, Excel | Чтение с SMB | **To-Be:** движок классификации до витрины, маскирование, **отдельные** проекты в Jupyter в K8s с секретами |

Обоснование в целом: цели To-Be (см. [Task 2](../Task2/c4-context-and-mvp.md)) требуют **конфиденциальности, целостности и доступности**; для классов **L3–L4** ущерб от утечки **существенно выше**, поэтому применяются более строгие меры и разделение доменов (**RBAC/ABAC по категориям** в MVP).

## 3. Сводка: шифрование и контроль по состояниям данных

| Состояние | Что имеется в виду | As-Is (инфраструктура и риски — см. Task 1, PRV) | Целевые инструменты (ориентир CTO: Java, PostgreSQL, ClickHouse, Elasticsearch, Kubernetes, Victoria Metrics) |
|-----------|-------------------|----------------------------|---------------------------------------------------------------------------------------------------------------|
| **At rest** | Данные на диске FileServer, в файлах 1С, Excel, бэкапах | Нет шифрования томов; нет аудита доступа к файлам | BitLocker/шифрование СХД или СУБД; **PostgreSQL** TDE/прозрачное шифрование; политики **Kubernetes** Secrets; шифрование снапшотов и носителей бэкапов |
| **In transit** | SMB, OLE/TCP между 1С, ККМ–1С, Exchange, будущие API | ЛВС без обязательного TLS на прикладном уровне; Exchange без гарантированного end-to-end контроля содержимого | TLS для API и сервисов; mTLS внутри mesh (**K8s**); VPN для удалённого админа; для лаборатории — **контракты API** с минимизацией полей |
| **In use** | Обработка в приложениях, Jupyter, отчёты | Нет маскирования; нет RLS на наборах | Динамическое маскирование, **row-level security** в PostgreSQL/ClickHouse, политики в **Elasticsearch**; изоляция namespace в K8s |

## 4. Реестр средств защиты (программные и аппаратные)

Ниже — связка **средство → назначение**; в As-Is часть позиций выполняет роль процесса/организации, не криптографии.

| Средство | Тип | Зона применения | Примечание |
|----------|-----|-----------------|------------|
| Active Directory / LDAP | Программная (IdM) | Аутентификация, группы | Нет MFA, нет ABAC на данных — усилить в To-Be |
| NTFS ACL / права на шары SMB | Программная | FileServer | Не заменяют шифрование at rest |
| Windows Server 2022, роли файлового сервера | ПО + аппаратный сервер | Хостинг SMB, AD | Единая точка отказа — см. Task 5 |
| 1С (файловый режим), OLE | ПО | Учёт | Канал без шифрования — закрывать сегментацией/TLS на уровне замены архитектуры |
| ККМ + драйвер 1С | Аппарат + ПО | Фискация | Физическая защита устройства |
| Exchange | ПО | Почта | Для CLS-02…04 — риск; DLP в To-Be |
| **PostgreSQL** (шифрование, RLS) | ПО | To-Be операционные данные | Якорь целостности и доступа по ролям |
| **Kubernetes** Secrets, политики сети | ПО | To-Be исполнение | Изоляция сервисов и секретов |
| **Victoria Metrics** / мониторинг | ПО | Наблюдаемость | Метрики попыток доступа, алерты (связь с UEBA в roadmap To-Be, Task 2/6) |
