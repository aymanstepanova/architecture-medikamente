# Task 2 — C4 Context и проект архитектуры MVP (To-Be)

Согласовано с As-Is и PRV в [Task 1](../Task1/data-privacy-problems-and-dfd-index.md) и с движком классификации в [Task 6](../Task6/c2-classification-engine.md). Границы MVP и развитие To-Be — в настоящем документе (§2, §6).

**Дисклеймер:** границы систем и протоколы — проектные допущения архитектора; детали контрактов API — уточняются при реализации.

## 1. Назначение диаграммы контекста

На уровне **C4 Context** показана одна целевая **программная система** — **платформа «Медикаменте»** (To-Be), с которой взаимодействуют люди и внешние системы. Внутреннее разбиение на сервисы на этом уровне **не раскрывается** (детализация на **C2 с конкретными технологиями** вынесена в [Task 6: C2 движка классификации](../Task6/c2-classification-engine.md)).

Файл диаграммы: [c4-context-mvp.drawio](c4-context-mvp.drawio).

---

## 2. Центральная система (MVP и развитие)

| Элемент C4 | Имя | Смысл |
|------------|-----|--------|
| **Software System** | Платформа «Медикаменте» | Единая цифровая среда компании: запись и учёт пациентов, платежи, интеграция с лабораторией, **категоризация данных и RBAC/ABAC по доменам** (MVP), слой **управления данными и конфиденциальностью** (классификация, политики, каталог), **аналитика с учётом политик** (согласование с Task 6). |

В MVP: пациент записывается через **портал**, ресепшен видит запись и может напоминать пациенту и врачу. Платформа должна поддерживать **разнесение категорий данных по доменам** и роли/атрибуты доступа.

---

## 3. Акторы (Person)

| Персона | Роль в кейсе | Связь с платформой |
|---------|----------------|---------------------|
| **Patient** | Пациент | Запись, ЛК, оплата, просмотр **своих** данных (цель на год) |
| **Doctor** | Врач | Расписание, доступ к данным по политике |
| **Administrator** | Ресепшен | Регистрация, журналы, напоминания (MVP) |
| **Cashier** | Кассир | Приём оплат через платформу / шлюз |
| **Bookkeeper** | Бухгалтер | Учёт (интеграция с учётным контуром в roadmap) |
| **Warehouse keeper** | Склад | ТМЦ (в периметре развития) |
| **Business analyst** | Аналитик IT | BI/отчёты только из **доверенных** витрин после классификации |

---

## 4. Внешние системы (External Software Systems)

| Система | Назначение |
|---------|------------|
| **Laboratory** | Внешняя лаборатория; обмен по **API** с минимизацией и изоляцией субъектов (см. потоки в §5) |
| **Payment network** | Внешний платёжный контур (эквайер / банк) для **платёжного шлюза** |
| **Legacy: 1С и файловый периметр** (опционально на схеме) | As-Is учёт; **миграция** данных в платформу (см. Task 5), не целевое состояние |

---

## 5. Основные потоки (согласованность с Task 6)

1. **Операционные** — пациенты и сотрудники работают с порталами и CRM через HTTPS; доступ по RBAC/ABAC.
2. **Лаборатория** — обмен только через контролируемый API (без избыточной утечки категорий данных).
3. **Аналитика** — данные для BI/ML поступают **после** слоя классификации и политик; на контекстной диаграмме этот слой входит в состав платформы как единый блок верхнего уровня; детализация — в [Task 6](../Task6/c2-classification-engine.md).

---

## 6. Privacy by Design (кратко)

- Минимизация и разделение доменов данных (MVP).
- Разделение ролей; в перспективе — теги, аудит, UEBA (roadmap To-Be, согласовано с Task 3/6).
- Новые интеграции проектируются так, чтобы **не перевалидировать** подход к данным при каждом партнёре (единая модель политик).
