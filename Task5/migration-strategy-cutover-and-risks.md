# Task 5 — Стратегия миграции, cutover-план, управление рисками

Кейс «Медикаменте». Опора: [Task 1 PRV](../Task1/data-privacy-problems-and-dfd-index.md) («монолит» файлов + Excel + 1С), [Task 4 Исикава](../Task4/migration-ishikawa-notes.md).

**Дисклеймер:** сроки и окна — **примерные** для учебного проекта; производственный cutover согласуется с бизнесом и DPO.

---

## 1. Обоснование выбора стратегии миграции

### 1.1. Контекст As-Is

Периметр миграции — не один модуль, а **связка файлового сервера (SMB), Excel и 1С** на одном контуре AD (см. [Task 1](../Task1/data-privacy-problems-and-dfd-index.md)). Целевое состояние — **платформа «Медикаменте»** ([Task 2](../Task2/c4-context-and-mvp.md)), **DWH** и **движок классификации** ([Task 6](../Task6/c2-classification-engine.md)). Риски сформулированы в PRV и на диаграмме Исикавы ([Task 4](../Task4/migration-ishikawa-notes.md)).

### 1.2. Выбранная комбинация подходов

| Подход | Смысл в проекте | Почему |
|--------|-----------------|--------|
| **Поэтапная миграция по доменам (phased)** | Сначала данные и процессы с наибольшей ценностью и видимостью для пациента (согласно MVP в [Task 2](../Task2/c4-context-and-mvp.md)), затем учёт, склад, лаборатория в полном API-контуре | Снижает «большой взрыв»; позволяет учиться на пилоте; ограничивает одновременный простой |
| **Параллельный прогон (parallel run)** для критичных финансовых и регламентированных участков | Период, когда **1С** и/или Excel-реестры сверяются с платформой до полного отключения Legacy | Снижает риск расхождений (PRV-007, двойной учёт); обязателен для кассово-бухгалтерского контура |
| **Strangler Fig (подмена по каналам)** | Новые операции (запись через портал) идут в новую систему; старые журналы Excel постепенно выводятся из оборота | Согласуется с ростом филиалов и нагрузкой без «одним релизом всё» |

**Не выбираем** чистый **big bang** для всех ПДн и медкарт: неприемлемый риск для целостности и конфиденциальности (см. эффект на диаграмме Исикавы).

### 1.3. Критерии готовности этапа (gates)

- Пройдены тесты миграции данных на копии (объём, качество, дубликаты).
- Политики RBAC/ABAC и классификация (CLS) согласованы с Task 3 для переносимых доменов.
- RTO/RPO для этапа зафиксированы; резервное копирование To-Be проверено.
- Обучение ключевых ролей (ресепшен, кассиры) и **runbook** cutover утверждены.

## 2. Cutover-план (структурированная таблица)

Условные роли: **CTO** — архитектор/техдир; **Ops** — админ сети/K8s; **PM** — владелец релиза; **DPO** — консультации по ПДн; **Lead reception / Lead cashier** — бизнес-сторона.

| Этап | Описание действия | Ключевые задачи | Ответственные | Время / сроки (пример) | Риски и меры по снижению |
|------|-------------------|-----------------|---------------|------------------------|-------------------------|
| **C0 — Подготовка** | Инвентаризация источников, маппинг P1–P8 → домены платформы | Каталог файлов/Excel; согласование идентификаторов пациента; freeze схемы переноса | CTO, PM, владельцы процессов | T0 − 8…12 недель | Неполнота инвентаря → **ревизия** по папкам FileServer; риск PII в теневых копиях → PRV-005/006 |
| **C1 — Инфраструктура To-Be** | Кластер **Kubernetes**, СУБД, секреты, сеть | Развёртывание; резервные копии; мониторинг (**Victoria Metrics**) | Ops, CTO | T0 − 6…10 недель | PRV-001 единый сервер As-Is → **не переносить** SPOF в prod без DR-плана |
| **C2 — Миграция справочников и P2** | Перенос **Patients.xlsx** / структуры в CRM; валидация дубликатов | ETL/скрипты; ручная выверка выборки | Ops + бизнес | Окно 1–3 дня + постобработка | Ошибки слияния дублей → **правила матчинга** ФИО+ДР+телефон; контрольная сверка количества записей |
| **C3 — MVP: запись на приём (P1)** | Портал + видимость в ресепшене; отключение **части** Excel-журналов по пилотному отделению | Cutover в нерабочие часы; переключение маршрута записи | PM, Lead reception, Ops | Выходные / ночь; 4–8 ч окно | Сбой записи → **откат** на Excel только для пилота; hotline |
| **C4 — Параллельный прогон платежей (P4)** | Касса: ввод в платформу **и** сверка с 1С/ККМ по дням | Ежедневные сводки; устранение расхождений (PRV-007) | Lead cashier, бухгалтерия | 2–6 недель | Расхождение сумм → **стоп-лист** по операциям; эскалация в бухгалтерию |
| **C5 — Cutover документов дела (P3)** | Перенос сканов в защищённое хранилище; отзыв избыточных прав SMB | Пакетная загрузка; контроль целостности (хэши) | Ops, CTO | Планово по объёму (batch) | Потеря файла → **верификация** по спискам; только инкремент после первого полного прохода |
| **C6 — Лаборатория (P7)** | Переключение на **API** после стабилизации контракта; закрытие ручного реестра поэтапно | Совместные тесты с лабораторией; миграция исторических Excel в DWH через движок ([Task 6](../Task6/c2-classification-engine.md)) | CTO, PM | После API-ready | PRV-008 ручной перенос → **контрольный журнал** до полного отключения Excel |
| **C7 — 1С: сокращение режима** | Вывод из онлайн-операций участков, перенесённых в платформу; сохранение архива/отчётности по регламенту | План простоя OLE; финальные выгрузки | Бухгалтерия, CTO | По графику налоговой отчётности | Блокировка учёта → **заморозка** изменений в 1С за N дней до выгрузки |
| **C8 — Стабилизация** | Наблюдение SLA, инциденты, доработки | War room 24–72 ч; ретроспектива | PM, все роли | +2 недели после major cutover | Пик обращений → **расширенная смена** ресепшена; FAQ |

## 3. Меры по управлению рисками (сводка)

### 3.1. Технические

| Риск | Источник | Мера |
|------|----------|------|
| Потеря или искажение данных при переносе | Разрозненные Excel, отсутствие версий | Контрольные суммы, двойная сверка объёмов, поэтапный freeze записей на Legacy |
| НСД при параллельной работе двух контуров | Две системы истины | Минимизация времени parallel run; аудит доступа к старому диску после cutover |
| Простой кассы/1С | OLE, файловый 1С | Окна вне пиков; откатный сценарий; предварительный прогон на копии базы |
| Неготовность классификации для DWH | Сырые данные без тегов | Не открывать витрины до прохождения движка Task 6; только Bronze с метками |

### 3.2. Организационные и комплаенс

| Риск | Мера |
|------|------|
| Ошибки персонала на новом UI | Обучение, чек-листы, суперпользователи на смене |
| Непонимание юридических сроков хранения | Вовлечение DPO до удаления Legacy-копий |
| Коммуникация с пациентами при сбоях записи | Заранее заготовленные сценарии (телефон, бумажный журнал только как временный fallback) |

### 3.3. Связь с Исикавой и Task 4

Категории **Данные**, **Legacy-приложения**, **Безопасность ПДн** из [migration-ishikawa-notes.md](../Task4/migration-ishikawa-notes.md) закрываются этапами **C2–C5**, **C4**, **C7** и техническими мерами §3.1. **Аналитика и DWH** — этапами после стабилизации операционного контура и включением пайплайна Task 6.

## 4. Откат (rollback)

- **C3 (журналы записи):** возврат к Excel-журналу пилотного участка при критическом дефекте; данные, введённые в платформу, экспортируются и сливаются вручную по процедуре.
- **C4 (платежи):** приоритет **целостности денежного учёта** — остановка приёма в новом контуре до выяснения; 1С остаётся источником истины на время расследования.
- Общий принцип: **сохранять возможность читать As-Is** до подписанного акта о завершении этапа.
